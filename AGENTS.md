# Agent instructions

This repository is an AI support platform with a reusable website widget. Read `README.md`, `ARCHITECTURE.md`, `DECISIONS.md`, `AI_ENGINEERING.md`, `SECURITY.md`, `TESTING.md`, and the latest `docs/handoffs/` file before changing architecture. The current repository has completed Phase 7; do not start Phase 8 until the owner approves it. Each app also has Next.js-generated `AGENTS.md` guidance; read the relevant installed Next.js docs before changing framework code.

## Coding and package rules

- Use Node.js, pnpm, strict TypeScript, and kebab-case filenames except framework-required names. Avoid `any`; document a genuinely unavoidable use.
- Keep direction `UI → application services → domain/adapters → infrastructure`. React components must not call GitHub, Jev, or the database directly. Keep the widget free of server-only imports and secrets.
- Use Zod at public API, environment, provider output, and webhook payload boundaries. TypeScript types are not runtime validation.
- Use Drizzle for PostgreSQL and reviewed migrations. Do not introduce Prisma. Use Better Auth when protected dashboard access becomes necessary; keep workspace authorization in application code.
- Keep Drizzle schema and queries in `packages/db`; application code imports its public repository/client boundary, not raw schema tables. Pass workspace/project context into protected reads and writes after authorization. Preserve the composite project-matching foreign keys and restrictive deletes.
- Keep `packages/widget` React-only and browser-safe. Import only its public package export from consumers. Its ShadowRoot styles are bundled; do not require consumer Tailwind configuration or import database/server code. Transport stays behind the `SupportSubmissionClient` interface; the demo keeps its mock for deterministic UI work alongside the real `HttpSupportSubmissionClient`. Never call a captured `fetch` as an instance method — resolve it at call time so the receiver stays undefined.
- Keep `packages/support-contracts` limited to stable cross-boundary request/response/error schemas. It must not import database, server, AI, or GitHub types.
- Keep `packages/ai` provider-neutral and server-only: the `TicketClassifier` interface, Zod schemas, Jev adapter, fixture classifier, policy, and triage service live there, with no database imports in core modules (the service takes a repository port; only CLIs wire the real repository). Jev receives only message and category hint, never contact details, IDs, or secrets. Route and escalation stay in deterministic policy code with documented thresholds.
- Keep `packages/auth` server-only except its `/client` entry: the Better Auth instance, session/membership helpers, and bootstrap CLI never reach the browser. Browser components import only `@ai-support-platform/auth/client`. Dashboard reads are server components over workspace-scoped repository queries; mutations are JSON route handlers with session, membership, Origin, Zod, and transition checks. Human decisions go to `ticket_overrides` with author and reason; AI history is never rewritten.
- Keep `packages/github` server-only with repository/tracker ports: the GitHub App client, deterministic drafts, privacy gate, and escalation service never touch the browser or database directly (CLIs and dashboard routes wire live dependencies). Escalation is operator-confirmed only; reconcile by marker before every create; human decline wins; ticket status is unchanged by creation. Mock tracker IDs derive from the issue marker so shared databases never collide.
- Add packages only for concrete phase needs. Use Biome as the default formatter/linter, adding ESLint only if a specific ecosystem check cannot be covered. Do not add Zustand, Redis/BullMQ, monitoring, or extra integrations without evidence and an ADR.
- Use Conventional Commits. Do not mix phases into a single change. A phase stops with a report and handoff.

## Current commands

Use Node.js 24 and pnpm 11.5.3. Run `pnpm install --frozen-lockfile`, `pnpm dev`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` from the root. Root dev/build compiles `packages/support-contracts` and `packages/widget` before starting apps; root dev also watches package changes. `pnpm dev:demo` builds the widget and starts only the demo. `pnpm test:e2e` builds shared packages once then serves both apps (`pnpm dev:e2e`); the ingestion specs need a migrated and seeded dev database. `pnpm format` applies Biome formatting. For database work, copy `.env.example` to ignored `.env`, run `pnpm db:up`, `pnpm db:migrate`, `pnpm db:seed`, `pnpm db:check`, and `pnpm test:db`. `pnpm db:generate` creates reviewed migration files; never use schema push for production. Both app scripts currently use Next.js `--webpack` as recorded in ADR-009. CI runs unit and PostgreSQL integration checks. `NEXT_PUBLIC_SUPPORT_API_URL` sets the demo's real-mode API target; `DATABASE_URL` stays server-only and `loadRootEnv` resolves the root `.env` for both package scripts and Next.js runtimes. `pnpm ai:triage --pending` and `pnpm ai:evaluate` run mock triage/evaluation with no credentials; `--classifier jev` requires `TYPESAFE_API_KEY` (plus optional `TYPESAFE_DEFAULT_MODEL`). `pnpm test:ai` runs the database-backed triage integration suite. `pnpm db:seed` also bootstraps the local dashboard owner when `SEED_OWNER_EMAIL`/`SEED_OWNER_PASSWORD` are set; dashboard E2E signs in with those seed credentials. `BETTER_AUTH_SECRET`/`BETTER_AUTH_URL` are required server-only env for `apps/web`. `pnpm github:connect` links a project to a GitHub App installation; `pnpm github:escalate --ticket <uuid>` creates via mock by default and `--live` with `GITHUB_APP_ID`/`GITHUB_APP_PRIVATE_KEY` (disposable repo only). `pnpm test:github` runs the escalation integration suite.

## Invariants

- Persist an accepted ticket before external AI or GitHub calls. Provider failure must not erase it.
- The widget project key is public identification, not authentication. Browser code never contains database, GitHub, TypeSafe, or generative-provider secrets.
- Tenant/project ownership is checked on every protected operation. A GitHub webhook updates only an issue linked to the matching installation and repository.
- Jev makes bounded recommendations; deterministic code owns policy and side effects. Validate normalized AI output and keep low-confidence cases in review.
- Never publish contact data, secrets, or raw private conversations to GitHub. Generated issue content passes the same publication checks as deterministic content.
- Ticket submission, work retries, issue creation, and webhook processing require documented idempotency and recovery. Do not blindly retry an ambiguous GitHub issue creation.

## Workflow

Before a phase, inspect current repository state and latest handoff. Make the smallest complete change for that phase. Update architecture and ADRs if behavior or boundaries change. Run relevant tests, typecheck, lint, and build checks that exist. Record commands and actual results, known issues, deferred work, and next-phase instructions in `docs/handoffs/phase-XX.md`. Never report an unrun check as passing. Use a disposable GitHub repository for integration testing before connecting a production repository.

Phase 8 implements signed GitHub webhook synchronization (close/reopen mapping) after separate approval, against the disposable repository first. Do not implement generative AI ahead of its phase. npm publication and portfolio installation require their later phases.
